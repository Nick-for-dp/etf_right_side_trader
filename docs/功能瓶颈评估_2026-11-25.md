# 功能瓶颈评估（2026-11-25）

评估方式：读 `README.md` / `Archi.md` / `PLAN.md` / `EXPERIMENT.md` / `Agent.md`，通读 `src/` 主链路代码，并对本机 PostgreSQL（`etf_trader`）做只读核查，跑了一次 `pytest`。

## 一、项目是什么

日线级 ETF 右侧趋势跟踪系统，不预测行情，只做"趋势确认后入场 + 风控触发后离场"，用门控拦截买入类建议。

- 主链路：`fetcher → quote → indicators(MA/MACD/BOLL/RSI/ADX/ATR/赔率) → strategy(BUY/SELL/HOLD) → risk(止损/90日持有) → advisor(建议+预算) → dashboard`
- 生产策略：`multi_indicator_scoring`，low_vol 用 v2.3 四子信号加权，high_vol 设计上用 `high_vol_balanced` 六子信号
- 执行规则：70/15/15 阶梯建仓、分市场/分波动止损、90 日最大持有、加仓冷却 5 天
- 门控：高溢价硬拦截、分市场（A股宽基 / NDX / HZ5017）gate-lite 极端下行拦截
- 实验层：`ablation.py` + `src/backtest/`，26 个实验矩阵，输出净值口径组合回测与归因报告
- 数据：BaoStock（日常 OHLCV）+ 东财（NAV/溢价）+ Tushare（历史）+ exchange_calendars

**结论先给：这个项目的瓶颈已经不在"再加一个因子"，而在"生产、回测、文档三者对不上，且数据链路和记账口径都在漏"。** 现在的系统无法证明自己跑的是文档里那个基线，也没法把漏掉的交易日补回来。

## 三、P0：生产一致性断裂（先修这个，否则所有实验结论都不可信）

### P0-1 文档基线与实盘配置不一致

- 现象：文档把 v2.5 当作当前生产对照，但实盘配置把 high_vol 信号 profile 关掉了；同时 `entry_budget_overrides.high_vol` 仍启用。
- 证据：`settings.yaml` 第 442-447 行 `enabled: false`；`settings.yaml.example` 第 329-331 行是 `enabled: true`；`create_strategy(config).version == "2.3"`。
- 影响：实盘是"v2.3 信号 + v2.5 预算分层"的混合体，既不是 v2.5，也不是干净的 v2.4。库里的 signals/advice、Dashboard、`backtest-portfolio`（读 DB signals）全部跑在 2.3 上，README 的 423 笔 / 15.12% 基线无法从当前环境复现。
- 建议：二选一并写死。要么开 profile + 全量 `rebuild-signals` 让实盘追上 v2.5；要么把文档基线降级为实际口径，并把 v2.5 明确标注为"回测候选"。

### P0-2 v2.5 信号在回测里是第二套实现

- 现象：`src/backtest/experimental_signals.py` 重新实现了一遍 `high_vol_balanced`，阈值 45/-35/18/3 直接硬编码，`signal_meta` 字段与生产策略类不同；回测风控也另写一套 `_check_risk` / `_stop_loss_threshold`，与 `src/risk/ProfileStopLossRule` 并行。
- 影响：策略和止损口径有两份真相。改一处、忘一处，回测结论就与实盘脱钩；而且没有任何测试能发现。
- 建议：提炼成"信号配置对象"，生产策略与实验信号共用同一个 `generate` 实现；回测直接调用 `RiskController`，只通过参数开关规则。

### P0-3 加仓预算（70/15/15）在实盘已经失效

- 现象：实盘 `add_count = trade_records_repo.count_adds(code, date)`，需求是"本持仓周期已加仓次数"，实现是"该 ETF 历史所有 ADD 条数"，SELL 不清零。
- 证据：`trade_records` 中 159870 有 **6 次 ADD**、159949 有 **3 次 ADD**，而 `add_steps` 只有 2 步。`_add_budget_check` 会直接返回 `add_budget:steps_used`，`_budget_plan` 返回 `{}`。
- 对比：回测用 `position.add_count`，新仓位自动归零。
- 影响：这两只当前持仓从此拿不到任何加仓建议和目标预算；回测验证的 70/15/15 与实盘不等价，"阶梯加仓"在生产上是断的。
- 建议：`count_adds` 改为"从当前持仓 entry_date（或最近一次 SELL）之后的 ADD 计数"，并在 `positions` 里显式维护 `add_count`；补一条跨周期回归测试。

### P0-4 90 日最大持有被加仓重置

- 现象：`PositionService.execute_buy` 在加仓分支执行 `old.entry_date = trade_date`，建仓日期被每次加仓覆盖。
- 证据：159870 的 BUY 流水是 2026-07-01，但 `positions.entry_date = 2026-07-07`（最后一次 ADD）；`operation_advice` 全库 `signal_source=max_holding` 记录为 **0**（部分是样本时间原因，但计时被重置是确定的）。
- 影响：只要在 90 天内加仓，计时就重置，最大持有规则会被无限推后；同理 STEP4 的 `peak_price` 也按被覆盖的 entry_date 计算，移动止损/回撤止盈同样失真。
- 建议：`positions` 增加 `first_entry_date`，加仓只更新成本与份额；风控与回测都读 `first_entry_date`。

### P0-5 仓库交付面不完整，基线不可复现

- 现象：`.gitignore` 排除了 `src/backtest/`、`ablation.py`、`tests/`，但 `main.py` 的 `backtest-odds` / `backtest-attribution` / `backtest-misjudge` / `backtest-portfolio` 分支 `import src.backtest`。
- 影响：clone 仓库后这些命令直接 `ImportError`；README 的标准回归与采纳门槛无法被第三方执行；"pytest 全绿"只是本机事实。这是"研究结论不可复现"的根因，比任何参数问题都严重。
- 建议：把回测引擎与实验配置纳入版本控制（大报告仍可放 docs）；`tests/` 至少纳入与生产口径相关的 8 个用例。

## 四、P1：数据链路漏点

### P1-1 NAV 与溢价率几乎是空的，而且已经停更

- 证据：`quote` 表 2016–2025 每一年的 `nav` 计数都是 **0**；有 NAV 的区间只有 **2026-01-05 ~ 2026-07-23**，共 3,428 行（而同期行情有 4,758 行）。`premium_rate` 同区间同条数。`indicators` 中 `odds_premium_blocked=True` 全库 **81 行（0.2%）**。
- 根因：历史由 Tushare `fund_daily + fund_adj` 回填，Tushare 不提供 NAV，代码有意不覆盖已有 NAV → 十年历史无净值；2026-07-23 之后东财 NAV 也没再更新。
- 影响：高溢价硬门控在 2023 年以前从未生效，2026 年只覆盖 1–7 月，**7 月 24 日之后溢价全程为 NaN、门控永久放行**。`LongTermOdds` 的价格基准在 2026 年 1 月从 `close` 切到 `nav`、7 月又切回 `close`，z-score/分位会出现两次台阶。另外 `close` 是前复权、`nav` 是未复权，混算溢价会在分红/拆分前后系统性偏差。
- 建议：用东财 `fund_etf_fund_info_em`（或 Tushare `fund_nav`）补齐 2016-2025 净值，再统一重算 premium 与 odds；同时明确"溢价用未复权价格算"，不要拿前复权 close 比 NAV。

### P1-2 断点不自愈，只补行情不补派生数据

- 证据：15 个交易日缺 `indicators`/`signals`/`market_regime`（2026-07-29、08-05、08-13、08-14、08-18~08-21、08-26~08-28、09-02~09-04、09-11），而 `quote` 对 2016-01-04~2026-09-14 的 2,600 个交易日**一天不缺**。
- 根因：`DataManager.sync_daily` 从 `latest+1` 拉到 T-1，行情能自愈；但 `STEP2/2B/3` 只计算 `T-1` 单日，漏掉的日子永久留空。补洞只能用 `init`（lookback 1500 天全量重算）或 `rebuild-signals`（只补 signals，不补 indicators/regime，且 advice 只重算最新一天并传 `risk_signals={}`）。
- 影响：回测在这些日子是空档；advice 无法按历史条件重放（缺风控信号），复盘和归因都失真。
- 建议：把 `run_daily` 改成"从最后一个完整派生日期补到今天"的区间编排（逐日补 indicators/regime/signals/advice，且 advice 用当日的真实 risk_signals 重算）。

### P1-3 管道已停摆 45 个交易日

- 证据：所有表最新日期停在 2026-09-14；最后一个交易流水 2026-08-04；持仓 3 只。
- 根因：`main.py schedule` 是前台进程 + 本机常开，APScheduler 无 misfire 处理、无失败重试、无告警，PC 不常开就等于不跑。
- 影响：Dashboard 打开即"暂无信号"；账户跟踪与建议全部停在 8 月。
- 建议：调度加"启动即补跑 + 失败告警（企业微信/飞书/邮件）"；或迁移到云主机定时任务。

### P1-4 门控依赖的指数覆盖不齐

- 证据：HZ5017 止于 2026-08-10；000813、000949 止于 2026-06-05；980022 仅 420 行且从 2024-12-23 开始。
- 影响：2026-08-11 起港股 ETF 的 regime 变成 `UNKNOWN`，而 `UNKNOWN` 不拦截 → 513180 的市场门控静默失效。主题热度实验所需的行业指数则根本不够长。
- 建议：把"指数最新日期"纳入每日健康检查并阻断流程；HZ5017 增加 AKShare 港股指数兜底。

### P1-5 市场热度门控基本没有信息量

- 证据：`market_regime` 2,585 天中 NORMAL 2,246（86.9%）、HOT_RISING 167、BEAR_TREND 85、UNKNOWN 60、HOT_FALLING 23、PANIC 3、RECOVERY 1；`operation_advice` 中被 market_regime 拦下的只有 **3 条**。
- 影响：gate-lite 实际只挡了约 4% 的交易日，而同期最大回撤 17–22%，说明它既不是回撤控制工具，也解释不了 BUY 亏损。溢价门控又基本失效，买入侧只剩"加仓冷却/预算"在起作用。
- 建议：先把门控从"状态标签"改成"可解释的连续风险分数 + 明确的阈值归因"，再用"被拦截信号后 5/10/20 日收益"验证它到底是避免亏损还是错过盈利（正是 PLAN 里那项未做的机会成本统计）。

### P1-6 "2016–2026 全池"其实是渐进扩池，长周期结论不成立

- 证据：27 只 ETF 中只有 6 只有 2016–2017 年数据（510150、513100、159949、512660、512880、512400），**21 只是 2019 年之后上市**，其中 561360（2023-10）、159326（2024-09）、159227（2025-05）、159278（2025-08）历史不足 3 年。
- 影响：所谓"2016-2026 全池 423 笔交易 / 15.12% 年化"，前三年实际只有 3–6 只 ETF 可交易，样本量随年份扩张；按"单 ETF 长周期表现"分出的 A/B/C 三类，各自样本窗口差异极大（159227 只有 312 条信号就参与了长周期分层）。这不是能直接下结论的历史池。
- 建议：把评估区间切到"池内 ETF 覆盖数 ≥ N"的起点（例如 2020 年起），或按"上市满 3 年"分组做 cohort 归因；PLAN 的采纳门槛应注明有效样本区间。

## 五、P1：实盘记账与执行口径

### 记账-1 减仓后成本被算错

- `PositionService.reduce`：`remaining_cost = cost*shares - sell_price*sell_shares`，再除以剩余份额。卖出价越高，剩余成本越低，极端情况为负。
- 影响：`pnl_pct`、止损阈值、Dashboard 浮盈浮亏全部偏离；应在减仓时保持单位成本不变，把卖出差额记为已实现盈亏。
- 证据：159870 现成本 0.8323，是在 6 次加仓 + 1 次减仓后算出来的，口径已不可解释。

### 记账-2 建议不可直接执行

- `target_position_ratio` / `target_budget_ratio` 是"占单 ETF 目标预算的比例"，不是占账户；没有金额、股数、可接受价格区间。
- `overview.py` 的 `_advice_reason` 把建仓预算硬写成"建仓预算 70%"，忽略 quality_tier 乘数（实际可能是 70%/56%/42%）。
- 建议：输出"目标金额 + 参考股数 + 允许滑点区间 + 该建议占账户比例"，并让文案读实际 multiplier。

### 记账-3 回测与实盘的资金分配规则不同

- 回测在没有相对强弱排序时，`_order_executable_advices` 原样返回，成交顺序约等于代码顺序；现金不足时"先到先得"。实盘则由人挑。
- 影响：同一天出现多个 BUY 时，组合结果取决于排序，而排序规则没有业务含义。这也是 PLAN 第一优先级"长周期分类资金配置"要解决的问题。

## 六、P2：策略与组合层

1. **逐日独立阈值，没有持仓状态**：423 笔交易 vs 280 笔，胜率 37.83% vs 39.64%。已试的 BUY/SELL 确认、最小持有、最大持仓数都在长区间让回撤变差 → 现在卡在"控不住频率也不敢控"的僵局。`TrailingStopRule` 代码存在但未启用，盈利回吐无规则。
2. **止损样本太少，无法校准**：423 笔闭合交易只有 7 次止损（high_vol 5 次），2024-2026 仅 1 次；而 90 日强平在实盘又因 P0-4 永不触发 → ATR profile 既没数据校准，也没被执行层验证。
3. **溢价阈值硬编码，且不分市场**：`LongTermOdds(premium_threshold=0.015)` 直接取默认值，不读配置。A 股 ETF 溢价常在 1% 附近，跨境 ETF 常年 2–10%，一旦 NAV 补齐，用同一阈值会系统性误杀 513100/513180（它们恰好是核心标的）。
4. **组合层没有行业/主题暴露约束**：27 只里科技主题占 5 只以上，可能同时持有多只同主题 ETF；现金平均 34%，但静态总仓/高波暴露/持仓数上限实验全部劣化 → 资金效率与回撤保护的结构矛盾没解。

## 七、P2：工程可维护性

1. 巨型模块：`portfolio_backtest.py` 2,061 行 / 81KB、`ablation_config.py` 74KB、`ablation_report.py` 49KB；单次回测的 `stats` dict 有 50+ 个计数键，每加一个实验就加分支。
2. 数据健康检查太浅：`check_data` 只查各表"最新日期"，不查缺失交易日、NAV 覆盖、指标完整度、指数停更 → 现在 15 天空洞 + 十年无 NAV，它仍全部报 OK。
3. 测试不覆盖生产契约：168 项全绿，但全是合成/mock 数据，没有一条"settings.yaml → signals → advice"的端到端一致性测试，所以 P0-1~P0-4 这类漂移一条都没被拦住。

## 八、建议的推进顺序

1. **先对齐口径（1–2 天）**：确定 high_vol profile 开/关；`rebuild-signals` 让 DB 与文档一致；修 `count_adds`、`first_entry_date`、`reduce` 成本三处记账；补一条端到端契约测试把这次修复锁死。
2. **让链路自愈（2–3 天）**：`run_daily` 改为区间补算，`check-data` 增加"缺失交易日 / NAV 覆盖 / 指数停更"三项硬校验，调度加失败重试与告警；先把 45 个交易日的空洞补回来。
3. **补 NAV（关键）**：回填 2016-2025 净值，统一重算 premium 与 `LongTermOdds`；否则溢价门控永远是装饰品。
4. **重跑基线再谈调参**：在 max_holding 真实生效、止损口径统一后，把 v2.4 / v2.5 各跑一遍，确认文档里的 15.12% / 22.06% 是否成立。
5. **做横截面资金分配**：把"同日多个 BUY 谁优先"显式化为 A/B/C 权重 + score 排序 + 现金分配规则，这是 PLAN P1 的第一项，也是当前最缺的一环。
